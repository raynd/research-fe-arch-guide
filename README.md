# Frontend Architecture for GEO & AEO

![Project started: 2026-11-04](https://img.shields.io/badge/started-2026--11--04-blue)
![Research phase: planning](https://img.shields.io/badge/research-planning-yellow)

A local-first, bilingual (English/German) research workspace for investigating how frontend architecture relates to machine readability, content extraction, retrieval, answer quality, and citation behavior in generative search systems.

**Project status:** Started on November 4, 2026. Research is currently in planning, and the workspace is under active development. Experiments have not been executed; hypotheses and architecture guidelines remain provisional, not validated findings. The documentation site remains available in English and German; this repository uses one English README.

## Run locally

Requires Node.js `>=22.23.4` and pnpm `11.25.0` (pinned in `package.json`).

Use pnpm exclusively; `pnpm-lock.yaml` is the authoritative dependency lockfile.

```sh
pnpm install
pnpm run dev
```

Build and preview:

```sh
pnpm run build
pnpm run preview
```

## Code quality and Git hooks

`pnpm install` runs Husky's `prepare` script to install the local Git hooks:

| Hook         | Check               | Scope                                                                                                                       |
| ------------ | ------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `pre-commit` | lint-staged         | Biome fixes staged JS/TS, JSON and CSS; Prettier formats staged Astro, Markdown/Markdoc and YAML.                           |
| `commit-msg` | commitlint          | Requires Conventional Commits, for example `feat(navigation): group architecture notes` or `docs: clarify research status`. |
| `pre-push`   | `pnpm run validate` | Biome, Prettier, Astro/TypeScript diagnostics and production build across the project.                                      |

Use `pnpm run lint:fix` for Biome fixes, `pnpm run format` for Prettier formatting, and `pnpm run validate` for the full check. Biome and Prettier have non-overlapping file ownership. Biome checks lint and formatting rules, **not TypeScript types**; `astro check` checks types, including Astro components. Markdoc uses Prettier's Markdown parser with embedded-language formatting disabled; do not treat formatting as Markdoc schema validation.

Generated files, local notes and the unmodified vendored Google skill are excluded. The pnpm lockfile is generated by pnpm, not formatted manually. Hooks provide fast local feedback but can be bypassed and are not a substitute for CI or branch protection; neither is configured yet. Existing historical commit messages are not rewritten.

## Git workflow: lightweight trunk-based development

`main` is the primary and normally active development branch. Small research-content changes may be committed directly: notes, literature and verified references, hypothesis refinements, findings, evidence assessments, guidelines, translations and corrections. Keep commits small, coherent and traceable; update paired EN/DE content together and preserve research IDs. A successful build validates the workspace, not the scientific claim.

Start routine work from a clean working tree:

```sh
git switch main
git pull --ff-only origin main
# Edit and review the relevant files.
git add <specific-files>
git diff --cached
git commit -m "docs(research): refine H-001 validation notes"
git push origin main
```

The existing hooks run on every branch: staged-file checks before commit, Conventional Commits validation for the message, and full validation before push. Fix failures rather than disabling hooks. If the pull or push cannot fast-forward, reconcile the histories before retrying; do not force-push shared `main`.

Use a short-lived branch and a Pull Request when isolation or review is valuable: larger architecture changes, new components or navigation, significant refactoring, experimental tooling, or substantial research changes needing review. Branch examples are `feature/...`, `experiment/...`, `refactor/...` and `fix/...`. These are temporary prefixes, not permanent branches. There is no `develop` or `release` branch and no branch/PR requirement for routine content edits.

```sh
git switch main
git pull --ff-only origin main
git switch -c feature/describe-the-change
# Edit, stage specific files and commit with a Conventional Commit message.
git push -u origin feature/describe-the-change
# Open a PR targeting main; review and merge while main is buildable.
git switch main
git pull --ff-only origin main
# Delete the merged temporary branch locally and on GitHub.
```

Use standard Conventional Commit types, such as `docs`, `feat`, `fix`, `refactor`, `test` and `chore`; optional scopes can identify research areas (`literature`, `hypotheses`, `evidence`) or the platform. Record source references, affected object IDs and reasons for changes where relevant. Experiments and literature assessments must remain explicitly provisional until documented evidence justifies a status change. The workflow is a team convention, not a new branch-enforcement hook.

## Research workflow

Content in `src/content/docs/` is the source of truth. Use Markdown (`.md`) for free-form notes and Markdoc (`.mdoc`) for structured hypotheses, experiments, and research objects. No database or external CMS is required.

The site separates the lifecycle into the dashboard, research foundation, literature review, notes, hypotheses, experiments, evidence, and final architecture guidelines. English is the default locale at `/en/`; German is at `/de/`. Starlight supplies the language selector and links equivalent pages when a translation exists.

Pages share the same filenames under `src/content/docs/en/` and `src/content/docs/de/`. This gives Starlight page-level translation pairing and English fallback with a visible untranslated notice if a translation is not yet available. Keep research IDs, statuses, and evidence classifications identical across locales; translate only their displayed labels. The literature register and findings matrix remain empty until sources or results are verified. Initial hypotheses and experiment briefs are proposals, not findings.

Object IDs are shared across languages. Existing IDs (`H-001`–`H-006` and `EXP-001`–`EXP-004`) are preserved; use `PAPER-###`, `HYP-###`, `EXP-###`, `FIND-###`, and `FE-###` for new research objects. Markdoc has one shared configuration; its status and evidence schemas are language-independent, while localized labels are supplied by each content file.

## Adding localized content

1. Add an English page under `src/content/docs/en/`, using a stable filename and locale-prefixed internal links such as `/en/01-foundation/questions/`.
2. Add the equivalent German file at the same relative path under `src/content/docs/de/`. Translate prose and frontmatter, but keep the filename, research IDs, status values, and evidence classifications aligned.
3. For Markdoc research records, use the shared tags and schemas. Keep canonical values such as `value="Proposed"` and `level="D"`; pass a translated `label` for German display.
4. Run `pnpm run check` and `pnpm run build`.

The Starlight sidebar uses localized page titles and translated group labels. Direct pages in sections 03 and 07 are listed in `sectionItems` in `astro.config.mjs`; add new direct page slugs there as well. Other sections and subgroup contents are autogenerated.

## Frontend agent skill

The project includes Google's [Modern Web Guidance](https://github.com/GoogleChrome/modern-web-guidance) as a GitHub Copilot project skill at `.github/skills/modern-web-guidance/`. It guides agents to consult current browser-platform practices before implementing relevant HTML, CSS, accessibility, performance, and client-side JavaScript changes. The skill uses Google's published CLI on demand; it adds no project dependency. Its source revision, attribution, and license are recorded alongside the skill.

The CLI can send anonymous usage data, including guide IDs and generated search queries, to Google. To opt out for a shell session, set `DISABLE_TELEMETRY=1` before running the CLI.

## Search engines and canonical URLs

Set `SITE_URL` to the canonical deployment origin when building for publication, for example `SITE_URL=https://research.example.org pnpm run build`. Starlight then emits absolute canonical and `hreflang` alternate URLs; no deployment hostname is hard-coded into local development. The sitemap uses the same Astro `site` value.

The experimental toolchain (including possible Python, PyTorch, BeautifulSoup, and Playwright evaluation tools) is deferred to a later research phase. No such tools or Python infrastructure are installed.

## AI agent setup

GitHub Copilot's always-on repository guidance is in `.github/copilot-instructions.md`. For focused work on the research workspace, select **Frontend Research Architect** from the Copilot agent picker; its profile is `.github/agents/frontend-research-architect.agent.md`. The profile builds on the Google Modern Web Guidance skill in `.github/skills/modern-web-guidance/` rather than duplicating it. A separate prompt file is unnecessary for this persistent project role; add `.github/prompts/*.prompt.md` only for repeatable, user-invoked task templates.
